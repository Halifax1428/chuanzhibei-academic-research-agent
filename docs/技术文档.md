# 科研论文智能体技术文档

**版本：** 1.0  
**日期：** 2026-11-18  
**项目形态：** 本地运行的 Web 科研助手（FastAPI + 单页前端）

## 摘要

本项目面向论文阅读、证据问答、文献管理和科研表达场景，提供本地运行的科研论文智能体。系统将 PDF/TXT/Markdown 文档解析为带页码和章节信息的文本片段，结合关键词与可选向量检索召回证据，再通过兼容 OpenAI Chat Completions 的模型服务生成回答。回答与跨论文比较均经过引用和证据覆盖检查；缺少模型凭据时，系统明确提示配置 API，不会以模拟模型伪装成功。

项目采用 FastAPI 提供本地 HTTP API，浏览器单页应用负责交互，SQLite 保存文献元数据、页面文本、索引、引用关系、翻译缓存及研究主题。核心代码位于 `langchain/agent/`。本技术文档依据仓库代码、配置、测试和本次实际测试结果编写。

## 1. 项目概述

### 1.1 建设目标

- 降低论文导入、定位、阅读、检索与整理的操作成本。
- 让模型回答尽量建立在已导入论文的可追溯证据上。
- 支持跨论文比较、外部论文发现、引用关系探索和科研写作辅助。
- 提供无需公网服务器的本地运行形态，便于演示、测试和个人使用。

### 1.2 项目边界

这是一个可运行的科研助手应用，而不是基础模型或通用自主代理平台。模型请求由项目内的异步 HTTPX OpenAI 兼容客户端直接完成；虽然依赖中包含 LangChain/LangGraph 相关包，当前核心问答链并未使用 LangChain Agent 或 LangGraph 编排。系统的确定性业务流程由普通 Python 服务函数和 FastAPI 路由控制。

## 2. 需求分析

| 需求 | 系统响应 | 验收关注点 |
|---|---|---|
| 复杂论文导入 | PDF 页面抽取、布局重排、低文本页 OCR、结构与参考文献启发式抽取 | 页面/章节定位；扫描件依赖 Tesseract |
| 论文去重与版本管理 | arXiv 标识、版本号、标题及文本相似度综合识别，向用户给出保留建议 | 误匹配允许人工决策；版本判断不宣称语义级完备 |
| 证据问答 | 混合检索召回片段，生成带引用回答并验证证据覆盖 | 证据不足或验证失败时拒答/隐藏答案 |
| 多论文推理 | 按所选论文分别检查证据覆盖，再组织比较与验证 | 不允许单篇证据替代另一篇论文证据 |
| 学术工具 | arXiv 搜索/下载/追踪、引用图谱、翻译、图表、写作框架、受限 Python 分析 | API/联网失败需给出明确反馈 |
| 本地可部署 | 环境配置、单命令启动脚本、SQLite 本地持久化 | 凭据不进入版本控制和交付包 |

## 3. 系统架构设计

| 层次 | 组件 | 主要职责 |
|---|---|---|
| 交互层 | 浏览器单页应用 `agent/static/index.html` | 论文阅读、工具入口、结果与证据展示 |
| API 层 | FastAPI `agent/main.py` | HTTP 路由、Pydantic 参数约束、错误响应和服务生命周期 |
| 领域服务层 | `document_service.py`、`agent_service.py`、`academic_search.py`、`citation_graph.py`、`copilot_service.py` | 文档处理、问答翻译、外部搜索、图谱与科研辅助 |
| 安全与模型层 | `python_sandbox.py`、`model_client.py` | 受限 Python 分析、OpenAI 兼容 API 调用 |
| 数据与外部依赖 | SQLite、本地上传目录、模型 API、arXiv API | 本地持久化、文件保存和外部模型/文献数据 |

单机默认绑定 `127.0.0.1:8000`，避免启动即暴露公网。上传文件、数据库和运行缓存保存在 `agent/runtime_data/`，由 `.gitignore` 排除。服务启动时确保本地运行目录存在；关闭时停止主题刷新任务。

### 3.1 主要 API 分组

| 分组 | 示例路由 | 用途 |
|---|---|---|
| 状态与文档 | `GET /api/health`、`POST /api/documents/upload`、`GET /api/documents/{id}/pages` | 健康检查、导入、文档页面/结构/引用读取、预览和去重决策 |
| 检索与问答 | `POST /api/retrieval/preview`、`POST /api/agent/ask`、`POST /api/agent/compare` | 查看召回证据、单篇问答和多篇比较 |
| 翻译 | `POST /api/agent/translate`、`POST /api/documents/{id}/translate` | 选段即时翻译和指定页全文翻译 |
| 外部论文 | `POST /api/search/arxiv`、`POST /api/search/arxiv/download`、`/api/tracks` | 搜索、下载、主题追踪和刷新 |
| 图谱与 Copilot | `POST /api/graph`、`/api/copilot/framework`、`/api/copilot/diagram` | 引用关系、综述线索、写作框架和图示代码 |
| 数据分析 | `POST /api/visualize/csv`、`POST /api/tools/python` | CSV 概览/图表和受限代码分析 |

完整请求模型与字段约束以 `langchain/agent/main.py` 中的 Pydantic 模型及路由实现为准。

## 4. AI 技术方案

### 4.1 技术选型与理由

- **OpenAI 兼容模型 API：** 可通过 `OPENAI_BASE_URL` 切换兼容服务，沿用用户已有模型服务；密钥由环境变量注入，不写入代码。
- **HTTPX 异步客户端：** 直接控制超时、请求和错误映射，降低模型层框架隐式行为，便于定位 API 不可用、配置缺失等问题。
- **本地检索优先：** 关键词检索可在未配置嵌入模型时工作；配置嵌入模型后使用向量召回并与词项检索融合，兼顾启动门槛与语义召回。
- **OCR 与 PDF 工具：** pypdfium2/pdfplumber/pypdf 完成文本与页面处理；低文本页可调用 pytesseract/Tesseract OCR。
- **SQLite：** 单用户、本地演示场景无需独立数据库服务，便于打包和恢复。
- **LangChain/LangGraph：** 当前依赖清单包含相关基础组件，但核心 AI 调用尚未接入这些框架；实际系统不以“使用 LangChain Agent”为技术卖点。

配置项位于 `langchain/agent/.env.example`：`OPENAI_API_KEY`、`OPENAI_BASE_URL`、`OPENAI_MODEL`、可选 `OPENAI_EMBEDDING_MODEL`、OCR 语言及刷新周期。没有模型配置时，模型功能返回明确的配置提示，不进行假回答。

### 4.2 集成方式与关键数据流

1. 用户选择 PDF/TXT/Markdown 上传；服务检查文件类型与大小限制，提取页面文本并保存本地副本。
2. 文档处理器重排部分双栏文本，识别标题、摘要、章节、图表标记和参考文献；低文本 PDF 页尝试 OCR。
3. 文本按页和章节切分，记录文献 ID、页码、章节与原文片段；可选建立嵌入索引。
4. 查询先按用户选择的文献范围过滤，再进行关键词与可用向量的混合检索，返回来源片段。
5. 模型只接收问题和检索证据，按结构化提示生成答案；程序检查引用标记及验证器结果，证据不充分时不展示为已支持结论。
6. 多篇比较逐篇检查召回和证据覆盖，要求每篇被选论文都有可用证据，随后再验证汇总答案。

### 4.3 抗幻觉与可追溯策略

- 检索结果包含原文、页码、章节和文献身份，可回到 PDF 对照。
- 答案校验检查引用标记与证据是否对应；校验服务不可用时采用失败关闭策略。
- 多篇比较要求每个选中文献均提供证据，缺少某篇证据时拒绝输出确定性比较。
- 写作框架只使用已检索到证据且可解析的规范参考文献条目。
- Future Work 与图谱匹配作为待核查线索呈现，避免将启发式关系表述为已证实事实。

### 4.4 优化策略

- 以文献 ID、章节、页码过滤，减少无关上下文。
- 关键词召回与可选向量召回融合；保留检索预览和评测 API 以观察召回结果。
- 对翻译保护 HTML/数学标记，并缓存页面翻译，降低重复模型请求。
- 将模型配置错误、网络请求错误及业务输入错误映射为可理解的 API 响应。
- 对上传体积、页数、输入文本、分析变量、循环和输出设置上限。

## 5. 核心功能实现

### 5.1 文档解析与版本管理

PDF 解析按页保留文本坐标/布局处理结果，并在文本稀少时尝试 OCR；文档结构、图表位置、章节和参考文献采用规则及启发式提取。版本识别优先利用 arXiv ID 与版本后缀，再结合标题和正文相似度。若版本证据不足则提示人工判断，允许保留旧版、保留新版或同时保留。

### 5.2 RAG 问答与比较

混合检索将候选片段回传给问答流程；模型生成后由校验流程确认引用可对应证据。跨论文比较有逐篇最低证据约束，避免“只检索到一篇却比较多篇”的错误。系统可通过检索预览接口查看检索证据，支持人工诊断。

### 5.3 学术搜索、引用图谱与推荐

外部搜索对接 arXiv Atom API，支持结果排序、PDF 下载、主题定期刷新和用户反馈排序。引用图谱在当前导入/搜索到的局部文献集上建立候选关系，并以 PageRank 类迭代计算节点重要度。边匹配依赖参考文献文本、标题及 arXiv ID；小范围局部图不能代表全领域引用网络。

### 5.4 科研 Copilot 与数据可视化

写作框架生成将 Idea 与相关证据结合，并校验参考文献身份；图示工具生成 Mermaid、Graphviz、TikZ 或 Matplotlib 代码。CSV 工具检查表头和行宽、生成确定性摘要与 SVG 图表，并输出图注草稿。其统计描述不替代研究者对数据质量、统计检验和科学解释的审核。

### 5.5 受限 Python 分析

代码先经 Python AST 解析，仅允许有限表达式、变量访问和有界循环等节点，再由项目定义的受限解释器执行；拒绝导入、属性访问、文件系统访问等能力，并限制数据规模与输出。该实现是应用层沙箱，不应作为面对恶意多租户代码的操作系统级隔离边界。

## 6. 测试与验收

### 6.1 本次可复现测试

2026-11-18 在项目虚拟环境中执行：

```powershell
Set-Location langchain
..\.venv\Scripts\python.exe -m unittest discover -s agent\tests -v
```

结果：**47 项测试全部通过**。覆盖 arXiv 追踪节流与错误反馈、证据校验与失败关闭、多论文逐篇证据门槛、引用图谱线索、CSV 输入边界和图表确定性、论文版本识别、扫描 PDF OCR 降级提示、翻译页数与页码校验，以及受限 Python 执行边界。

此前隔离验收曾通过 arXiv 下载并解析 20 篇论文（381 页、0 失败），构造 20 节点、39 条候选引用边；该记录是一次临时数据集验收，不代表所有领域或所有 PDF 均达到同等解析质量。正式运行数据库不包含这批临时数据。

### 6.2 当前能力边界与风险

- 复杂公式、表格与图像语义仍可能解析不完整；当前不具备通用视觉模型级图表理解。
- 双栏重排、标题/章节、参考文献和引用关系以启发式为主，错误候选需要用户复核。
- PDF OCR 依赖本机安装 Tesseract 及语言数据；未安装时应查看服务提示并安装 OCR 组件。
- 嵌入检索需要兼容的 Embedding API；无嵌入配置时依赖词项检索，召回能力会不同。
- 外部 arXiv 搜索和模型调用均需要联网；外部服务不可达时相应功能不能完成。
- 本地 SQLite 面向单机使用，不提供用户权限、团队协作、备份恢复界面或公网级安全管理。
- 测试以自动化单元/接口逻辑为主；真实模型输出存在服务商、模型版本和网络差异。

## 7. 部署与运行

### 7.1 环境要求

- Windows 10/11 或支持 Python 3.10+ 的桌面环境。
- 可联网访问所配置的模型 API；需要外部论文搜索时可访问 arXiv。
- 扫描件 OCR 需安装 Tesseract 与中文/英文语言包。
- 使用向量检索时，另需兼容的嵌入模型服务和模型名。

### 7.2 启动步骤

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item langchain\agent\.env.example langchain\agent\.env
# 在本机编辑 langchain\agent\.env，填写模型服务配置
Set-Location langchain
python -m uvicorn agent.main:app --host 127.0.0.1 --port 8000
```

浏览器访问 `http://127.0.0.1:8000/`。Windows OCR 可运行 `langchain/agent/setup_ocr.ps1`。API 密钥只能填写在本地 `.env`，不得提交到 Git、压缩包或公开文档。没有 API 时，应用会提示添加配置。

### 7.3 数据与安全

原始上传文件、SQLite 数据库和翻译缓存仅在本地运行数据目录保存。上传限制、参数约束和受限代码执行减少误操作面，但不等于完整的公网安全方案。当前项目适合本地演示与个人科研工作流；公开部署前还需补充身份认证、请求限流、HTTPS、数据备份/删除策略、隔离运行和隐私告知。

## 8. 创新点

### 8.1 技术创新点

1. **证据门控的科研问答：** 将检索片段、页码/章节来源、引用检查和验证器失败关闭组合为一条可检查的数据流。
2. **跨论文逐篇证据约束：** 每篇被选论文均需达到证据门槛，再生成对比结果，减少单篇证据外推。
3. **面向论文版本的导入管理：** 结合 arXiv 标识/版本、标题和内容相似度给出版本处理建议，并保留人工决策入口。
4. **检索、阅读与引用线索闭环：** 从导入、页面定位、引用抽取到局部关系图谱和综述线索在同一工作台串联。
5. **受限分析与结构校验：** 对 Python AST、CSV 结构、翻译页码、上传大小和图示标签进行输入边界控制。

### 8.2 应用创新点

1. **把“给模型提问”转成“选文献、看证据、再接受结论”的科研阅读流程。**
2. **在同一系统串起论文阅读器、选段翻译、整篇翻译、外部文献追踪与科研写作辅助。**
3. **将论文证据、引用图谱和数据图表辅助放入可本地运行的单机工作台，降低部署与试用门槛。**
4. **对不确定的版本、图谱边和 Future Work 保留提示/复核，而非将候选算法结果包装为确定结论。**

## 9. 总结与展望

当前版本已形成从本地论文导入、解析、检索、证据问答、多文比较到引用探索和科研表达的可运行闭环，并通过 47 项自动化测试。它的重点是可追溯和可控的应用流程，而非宣称解决学术 PDF 的全部理解难题。

后续可以优先推进：增加多模态图表/公式解析与版面基准集；将引用匹配接入 DOI、OpenAlex、Semantic Scholar 等权威元数据；建立端到端问答与检索评测集；补充任务队列和可恢复索引；增加账户、审计、备份和安全部署配置；对 LangGraph 工作流进行显式化并保持每一步可追溯。任何升级均应以可复现测试和失败案例为准。
